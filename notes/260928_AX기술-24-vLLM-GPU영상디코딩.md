# 영상 캡셔닝의 병목은 GPU가 아니라 CPU 디코딩이었다 — vLLM의 NVDEC 하드웨어 디코딩 지원

> 정리일: 2026-09-28
> 출처: [vLLM Blog (NVIDIA NVCV 팀) — Scaling Multi-GPU Video Captioning with PyNvVideoCodec and vLLM](https://vllm.ai/blog/2026-09-18-pynvvideocodec)
> 발행일: 2026-09-18
> 원문 언어: 영문

## 한 문장 인사이트
이 글은 다중 GPU 영상 캡셔닝이 GPU를 늘려도 빨라지지 않는 문제에 대해 **영상 디코딩을 CPU에서 GPU 하드웨어 디코더(NVDEC)로 옮기는 방법**을 제시한다. 근거는 H100 1~8장 처리량과 CPU 사용률 비교이고, 한계는 **디코딩용 VRAM을 따로 떼어야 하고 NVIDIA 자체 측정 한 가지 설정**이라는 점이며, 내 작업에서는 **GPU를 늘리기 전에 CPU 사용률이 먼저 포화되는지**를 확인해 보겠다.

## 원문 요약
- vLLM이 NVIDIA GPU 내장 하드웨어 영상 디코더를 쓰는 **PyNvVideoCodec 백엔드**를 지원한다. 표준 CUDA vLLM 릴리스에 포함돼 있다(`PyNvVideoCodec==2.0.4`).
- 기존에는 영상을 **CPU 기반 OpenCV+FFmpeg**로만 디코딩했다. GPU마다 vLLM 서버를 하나씩 띄우면 모든 서버가 CPU에 디코딩을 요구한다.
- 영상 캡셔닝은 출력이 **100~200토큰**으로 짧아 전체 시간에서 디코딩 몫이 크다. 그래서 **GPU 2~4장만으로도 CPU 코어가 포화**된다.
- 사례는 NVIDIA 자율주행(AV) 조직의 캡셔닝 작업이다. 수십만 시간 분량 클립, **수억 건의 캡셔닝 요청**을 `Qwen3-VL-8B-Instruct` 같은 가벼운 모델로 처리한다.
- 운영 방식: CUDA MPS 데몬을 먼저 띄우고, GPU 1장당 vLLM 복제본 1개(컨테이너 또는 `CUDA_VISIBLE_DEVICES`), 앞에 리버스 프록시로 요청을 나눈다. `--mm-ipc-gpu-memory-gb`로 디코딩용 VRAM을 예약한다.

> "CPU-based video decoding can quickly become a bottleneck, maxing out CPU cores even with just 2 or 4 GPUs."
> (CPU 영상 디코딩은 GPU 2~4장만으로도 CPU 코어를 모두 써 버리는 병목이 된다.)

## 핵심 주장과 근거
- **주장 1: CPU 디코딩은 GPU 수를 늘릴수록 먼저 막힌다.**
  - 근거(원문 그림, H100 80GB, Xeon 8480C 112코어, 1080p→1024×576 16프레임, 입력 300·출력 100토큰): CPU 평균 사용률이 GPU 1장 **55.5%** → 2장 94.1% → 4장 99.0% → 8장 **99.9%**.
  - 같은 조건에서 NVDEC 사용 시 CPU 사용률은 3.0%·12.3%·14.4%·24.3%, NVDEC 사용률은 78~87%.
- **주장 2: 하드웨어 디코딩으로 8 GPU까지 처리량이 늘어난다.**
  - 근거(초당 처리 클립 수, CPU 디코딩 → NVDEC): 1장 3.5 → 3.6, 2장 6.0 → 7.1, 4장 9.3 → 14.0, 8장 **12.0 → 27.3**. 8장에서 **2배 이상**.
  - 1장에서는 차이가 거의 없다. 이득은 CPU가 포화되는 다중 GPU 구간에서 생긴다.
- **한계·반론:**
  - 영상 디코딩에 VRAM을 따로 예약해야 한다. KV 캐시가 VRAM을 이미 다 쓰는 경우 영향이 있을 수 있다고 원문이 밝힌다. 다만 "실제 테스트에서 성능이 나빠진 경우는 보지 못했다"고 쓴다.
  - 결과는 한 모델·한 해상도·한 하드웨어 조합의 NVIDIA 측정이다. 출력이 긴 과제나 CPU 코어가 더 많은 노드에서의 결과는 원문에 없음.

## 읽고 얻은 관점
- 멀티모달 추론에서 **전처리(디코딩·리사이즈)도 추론 파이프라인의 일부**다. GPU를 늘려도 처리량이 안 늘면 모델이 아니라 입력 준비 단계를 먼저 봐야 한다.
- 출력이 짧을수록 모델 연산 몫이 작아지고 전처리 병목이 드러난다. 앞 노트의 VLM 추측 디코딩(→ [LFM2.5-VL-DSpark](260928_AX기술-23-LiquidAI-VLM-추측디코딩.md))과 같은 논리다: 가속하지 않는 구간이 전체를 제한한다.
- 대규모 데이터 라벨링(자율주행 장면 설명, 검색용 메타데이터)은 "배치 VLM 추론"이라는 별도 워크로드다. 처리량(clips/s)과 CPU·NVDEC 사용률이 지연보다 중요한 지표가 된다.

## 적용 질문
- 작은 실험: GPU 1장 환경에서 짧은 영상 100개를 vLLM으로 캡셔닝하면서 `top`/`nvidia-smi`로 **CPU 사용률·GPU 사용률·clips/s**를 기록한다. 이어 프로세스 2개(또는 동시 요청 수 2배)로 늘려 CPU가 먼저 100%에 닿는지 본다. 가능하면 `--media-io-kwargs`의 backend를 pynvvideocodec으로 바꿔 같은 표를 다시 만든다.
- 내 멀티모달 파이프라인에서 이미지·영상·오디오 전처리는 CPU·GPU 중 어디서 도는가? 요청당 전처리 시간을 따로 로그로 남기고 있는가?
- 디코딩용 VRAM 예약이 KV 캐시 여유를 줄여 동시 처리 수를 떨어뜨리지 않는지, 예약량을 바꿔 가며 확인할 수 있는가?

## 읽을 때 주의할 점
- NVIDIA 팀이 자사 하드웨어 기능을 vLLM에 통합하고 쓴 글이다. 수치는 모두 자체 측정이다.
- AV 조직의 "수억 건 요청" 규모는 작업 규모 설명이며, 이 기능 도입 후 운영 절감 효과(시간·비용)는 원문에 없음.
- 원문 예시 프롬프트·출력은 설명용이며 실제 프롬프트는 더 길고 구조적이라고 원문이 밝힌다.
