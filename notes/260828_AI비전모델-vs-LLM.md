# AI 비전 모델 서비스, LLM과 어떻게 다를까?

> 정리일: 2026-08-28
> 배경: 그동안 학습은 주로 LLM 기반 생성형 AI에 집중되어 있었다. 언어 데이터 처리 수요가 압도적으로 많았기 때문이다.
> 하지만 Physical AI(로봇, 자율주행 등 물리적 세계와 상호작용하는 AI)가 확산되면서 이미지·영상을 다루는 비전(Vision) 모델에 대한 이해도 함께 필요해지고 있다.
> LLM을 먼저 배웠든 비전 모델을 먼저 배웠든, Physical AI 시대에는 결국 두 축 모두 필요하다.

---

## 한 문장 인사이트
이 글은 Physical AI 시대에 비전 모델과 LLM의 차이를 **판별형·생성형·VLA 세 층위**로 나눠 보는 틀을 제시하며, 근거는 서빙·데이터 파이프라인·지연·LoRA 운용의 구조 비교이고 한계는 **실측 수치 없이 구조 비교에 머문다**는 점이다. 내 작업에서는 **채용 공고 키워드로 준비할 층위를 판별**해 보겠다.

## 원문 요약

"AI 비전 모델"은 한 가지를 가리키는 말이 아니다. **크게 두 갈래**로 나눠 이해하면 훨씬 명확해진다.

| 갈래 | 하는 일 | 대표 모델 | 출력 |
|---|---|---|---|
| **판별형 (Discriminative)** | 인식한다 | YOLO, ResNet, Segmentation 계열 | 라벨 · 좌표 · 마스크 |
| **생성형 (Generative)** | 만들어낸다 | Stable Diffusion, GPT Image, Nano Banana / Pro | 새로운 이미지 |

그리고 우리가 배운 **LLM은 이 중 생성형 쪽에 속하는 "텍스트 버전"** 이라고 보면 된다.

여기에 한 층위를 더 얹으면 **VLA(Vision-Language-Action) / Physical AI** 가 된다.

---

## 핵심 주장과 근거

### 1. 판별형 비전 모델 — "인식하는 AI"

이미지를 입력받아 **"이게 무엇인지" 판단**하는 모델.

- **모델**: YOLO(객체 탐지), ResNet 등(분류), Segmentation 모델
- **출력**: 라벨 · 좌표 · 마스크 같은 "판단 결과"
- **목적**: 무언가를 새로 만드는 것이 아니라 **이해·분류**
- **서비스 예시**: CCTV 분석, 제조 결함 검사, 리테일 분석

#### LLM 서비스와의 구조적 차이

**모델 서빙 방식**
LLM은 보통 텍스트 스트리밍 기반 API 호출 구조(토큰 단위 응답)다.
반면 판별형 비전 모델은 이미지·영상 **전처리 파이프라인(리사이즈, 정규화)**, 배치 추론, GPU 메모리 관리, 실시간 프레임 처리 같은 이슈가 추가된다.

**데이터 파이프라인**
이미지·영상 데이터는 **저장·전송 비용이 크다**. 스트리밍 처리(WebRTC, RTSP 등)나 비동기 큐 처리 구조가 필요한 경우가 많아, 일반 웹 서비스나 텍스트 기반 LLM 서비스와는 다른 인프라 설계가 요구된다.

**지연시간(latency) 요구사항**
실시간 비전 서비스(CCTV 분석, 실시간 객체 탐지 등)는 **응답 속도에 훨씬 민감**하다. 그래서 엣지 추론이나 모델 경량화(quantization, ONNX 변환) 같은 주제까지 다뤄야 할 수 있다.

---

### 2. 생성형 비전 모델 — "만들어내는 AI"

텍스트나 이미지를 입력받아 **새로운 이미지를 만들어내는** 모델.

- **모델**: Stable Diffusion(Stability AI), GPT Image(OpenAI), Nano Banana / Nano Banana Pro(Google Gemini)
- **서비스 예시**: 이미지 생성 서비스, 이미지 편집·보정 서비스

#### LLM 서비스와의 구조적 차이

**모델 서빙 방식**
디퓨전 모델은 한 번의 요청에 **여러 스텝의 반복 추론**(denoising step)이 필요하다.
LLM의 토큰 단위 스트리밍보다는 **"긴 단일 작업(job)을 처리"하는 구조**에 가깝고, 요청당 GPU 점유 시간이 훨씬 길다.

**데이터 파이프라인**
실시간 스트리밍보다는, 생성 요청을 큐에 쌓고 비동기로 처리한 뒤 결과 이미지를 저장·전달하는 구조(**작업 큐 + 오브젝트 스토리지**)가 중심이 된다.

**지연시간 요구사항**
실시간 탐지만큼 촉박하지는 않다. 대신 **"생성 품질과 속도의 트레이드오프"**(스텝 수 조절, LCM 같은 경량화 기법)가 핵심 이슈가 된다.

**파인튜닝(Fine-tuning) 방식** ← 특히 LLM과 크게 갈리는 지점
- 이미지 생성 모델은 **LoRA(Low-Rank Adaptation) 여러 개를 동시에 병렬로 붙여 쓰는 경우가 흔하다.**
  예: "캐릭터 스타일 LoRA" + "특정 화풍 LoRA" + "포즈 LoRA"를 각각 다른 가중치로 함께 적용해 원하는 결과를 조합.
  → 이미지의 스타일·구도·개체 같은 요소들이 비교적 서로 **분리(disentangle)** 되어 있어서, 여러 LoRA를 합성해도 상대적으로 안정적으로 작동하기 때문.
- 반면 **LLM은 보통 하나의 LoRA 어댑터를 하나의 태스크·도메인에 맞춰 학습**하고, 서빙 시에도 요청에 따라 어댑터를 교체하는 방식(멀티 LoRA 서빙, 예: S-LoRA)이 일반적이다.
  → 언어적 의미는 여러 요소가 서로 **얽혀(entangle)** 있는 경우가 많아, 여러 LoRA를 동시에 합쳐 쓰면 충돌이나 품질 저하가 발생하기 쉽기 때문에 자유롭게 병렬 결합하지 않는다.

---

### 3. 한 걸음 더 — 물리적 행동까지 이어진다면

지원하는 회사가 **로봇, 매니퓰레이터, 자율주행, 드론**처럼 물리적 장치를 제어하는 제품을 다룬다면 이야기가 한 층 더 확장된다.

인식이나 생성에서 그치지 않고, **비전 입력 + 언어 지시를 함께 받아 실제 물리적 행동(action)을 출력하는 VLA(Vision-Language-Action) 모델**까지 다뤄야 할 수 있다.
이는 **Physical AI(임베디드 지능)** 영역으로, 앞의 두 갈래와는 또 다른 층위의 설계 지식이 필요하다.

---

### 4. 세 축 비교 요약

| 항목 | LLM | 판별형 비전 | 생성형 비전 |
|---|---|---|---|
| 서빙 구조 | 토큰 단위 스트리밍 API | 전처리 파이프라인 + 배치/실시간 프레임 추론 | 긴 단일 job (multi-step denoising) |
| 데이터 파이프라인 | 텍스트 중심, 가벼움 | 스트리밍(WebRTC/RTSP), 비동기 큐, 대용량 저장/전송 | 작업 큐 + 오브젝트 스토리지 |
| latency | 첫 토큰 지연 중심 | **매우 민감** (엣지 추론, quantization, ONNX) | 상대적 여유, 품질↔속도 트레이드오프 |
| GPU 점유 | 요청당 짧고 잦음 | 프레임 단위 지속 점유 | 요청당 길게 점유 |
| LoRA 운용 | 태스크당 1개, 서빙 시 교체(S-LoRA) | (해당 적음) | 여러 개 병렬 합성 (스타일+화풍+포즈) |

---

## 읽고 얻은 관점

- 비전 모델은 **판별형 / 생성형**으로 먼저 나눠 이해한다.
- 필요하다면 **VLA / Physical AI**까지 확장해서 준비한다.
- 이 **세 층위**를 다 알아두면 면접 질문의 방향에 따라 유연하게 대응할 수 있다.

## 적용 질문

### 채용 공고에서 층위 판별하기

공고나 프로젝트 설명에 다음 단서가 있는지 확인하면, **어느 층위를 준비해야 할지** 가늠할 수 있다.

| 키워드 | 준비할 층위 |
|---|---|
| `detection`, `classification`, `recognition` | 판별형 비전 모델 |
| `generation`, `diffusion`, `text-to-image` | 생성형 비전 모델 |
| `action`, `control`, `manipulation`, `policy` | VLA / Physical AI |
