# 맥 로컬 추론의 문제는 동시 요청이다 — vllm-metal이 애플 실리콘에 가져온 스케줄러와 페이지 KV 캐시

> 정리일: 2026-09-28
> 출처: [vLLM Blog — Announcing vllm-metal: Concurrent Serving on Apple Silicon](https://vllm.ai/blog/2026-09-22-vllm-metal-v0-28-0)
> 발행일: 2026-09-22
> 원문 언어: 영문

---

## 한 문장 인사이트
이 글은 Mac 로컬 추론이 여러 요청이 겹칠 때 느려지는 문제에 대해 **vLLM의 스케줄러·페이지 KV 캐시를 MLX/Metal 위에 얹는 방법**을 제시한다. 근거는 SiliconBench 에이전트 부하에서 잰 동시성별 TTFT·지연 비교이고, 한계는 **동시성 1에서는 다른 엔진이 앞서고 일부 기능이 실험 단계**라는 점이며, 내 작업에서는 **코딩 에이전트 여러 개를 붙였을 때 동시성 1·4·8의 TTFT**를 확인해 보겠다.

## 원문 요약
- vLLM 프로젝트가 애플 실리콘용 플러그인 **vllm-metal**의 첫 공식 릴리스 v0.28.0을 발표했다(현재 v0.29.0, Homebrew 설치).
- 원문 문제 설정: Mac 로컬 추론은 요청이 겹치기 전까지는 쉽다. 겹치면 **TTFT·메모리 증가·요청 수용 제어**가 모델 실행이 아닌 **서빙 문제**가 된다.
- 역할 분담: 상위 vLLM이 V1 스케줄러·페이지 KV 블록 관리·chunked prefill·샘플링·OpenAI 호환 서버를, mlx_lm이 모델 구현을, MLX·Metal이 실행을 맡는다.
- mlx_lm의 토큰 단위 층(RMSNorm·Linear·MoE·MLP)은 그대로 쓰고, 요청 경계가 필요한 **어텐션만 페이지 varlen Metal 커널로 교체**했다. 이 커널은 vLLM의 통합 Triton 어텐션 커널을 이식한 것이다.
- `--gpu-memory-utilization`으로 추론 메모리 예산을 정한다. 시작 시 워밍업으로 가중치·활성값을 계산한 뒤 **남은 예산을 고정 KV 캐시로 할당**하고, KV 풀에 안 들어가는 요청은 페이지가 빌 때까지 기다린다.
- v0.28.0에는 배치 MTP(Gemma 4), GGUF, 하이브리드 모델(Qwen3.5 계열 등), M5 NAX 프리필 커널, LoRA, 구조화 출력, 다중 Mac 파이프라인 병렬 등이 들어갔다.

> "Then time to first token (TTFT), memory growth, and admission control become serving problems rather than model-execution problems."
> (그때부터 TTFT, 메모리 증가, 요청 수용 제어는 모델 실행 문제가 아니라 서빙 문제가 된다.)

## 핵심 주장과 근거
- **주장 1: 패딩 대신 패킹하면 길이가 들쭉날쭉한 배치에서도 느려지지 않는다.**
  - 근거(자체 측정, Qwen3.6-35B-A3B 4bit, 요청 8개·총 약 6,000 프롬프트 토큰·요청당 출력 20토큰, 배치 시간 초): 길이가 비슷한 배치 A → 긴 프롬프트 하나가 섞인 배치 B에서 **mlx_lm 4.52 → 10.99초(+143%)**, vllm-metal 3.87 → 3.64초(−6%), llama.cpp 5.29 → 5.33초, oMLX 7.32 → 7.22초.
  - 방식: 모든 요청의 쿼리 토큰을 `[total_q, H, D]`로 이어 붙이고 `cu_seqlens`로 경계를 표시해 **한 번의 forward**로 처리한다. KV는 요청별 블록 테이블로 가리키는 고정 크기 페이지에 저장한다.
- **주장 2: 동시 에이전트 부하에서 TTFT가 낮다.**
  - 근거(SiliconBench 에이전트 분할: 약 4.6K 입력 토큰 멀티턴 프롬프트 100개, M5 Pro 64GB, 4bit): Qwen3.8-27B에서 **동시성 2·4의 TTFT와 전체 지연이 가장 낮다**. Gemma 4 E4B에서는 동시성 16까지 TTFT를 낮게 유지했다. Qwen3.6-35B-A3B 동시성 4에서는 RAM 캐시 oMLX와 처리량·지연이 비슷하고 TTFT 차이가 더 컸다.
  - 벤치마크 스크립트·서버 설정을 SiliconBench 저장소와 부록에 공개했다.
- **주장 3: 배치 MTP는 동시성에 따라 효과가 달라진다.**
  - 근거(Gemma 4 E4B, 드래프트 토큰 1개, MTP 없음 대비): 동시성 1에서 벽시계 시간 −15%·출력 tok/s +20%, 동시성 8에서 거의 차이 없음(−1%, +0%), 동시성 16에서 −8%·+9%지만 **평균 TTFT +20%**.
- **한계·반론:**
  - Qwen3.8-27B **동시성 1에서는 SSD 오프로드 oMLX가 앞선다**.
  - MTP는 Gemma 4, greedy(`temperature=0`), 동기 스케줄링에서만 지원한다. 하이브리드 모델 prefix caching은 실험 단계이며 추측 디코딩과 함께 쓸 수 없다. VLM·임베딩·음성 인식도 실험 단계다.
  - 엔진마다 자체 4bit 변환과 다른 메모리 설정을 썼다. 비교는 vLLM 측이 설계·실행했다.

## 읽고 얻은 관점
- 로컬 LLM 성능은 "토큰/초 한 줄"로 비교하면 안 된다. 요청이 하나일 때와 여러 개일 때 1등이 바뀐다. 에이전트·여러 세션이 한 서버를 쓰는 순간 **스케줄러와 KV 메모리 관리**가 성능을 결정한다.
- vllm-metal의 설계는 "바꿀 곳만 바꾼다"의 예다. 토큰 단위 층은 재사용하고 요청 경계가 필요한 어텐션 한 층만 새로 짰다.
- 고정 KV 풀 + 대기열 방식은 메모리 초과로 죽는 대신 **기다리게 만드는** 선택이다. 노트북처럼 다른 앱과 메모리를 나눠 쓰는 환경에서 예측 가능성을 준다.
- 멀티턴 에이전트는 매 턴 대화 전체를 다시 보낸다. prefix caching이 TTFT에 직접 영향을 준다.

## 적용 질문
- 작은 실험: Mac에서 `vllm serve`(vllm-metal)와 `llama-server`로 같은 소형 4bit 모델을 띄우고, `vllm bench serve`로 약 1K 입력·128 출력 프롬프트 100개를 **동시성 1·4·8**에서 보내 평균 TTFT·출력 tok/s·성공 요청 수를 표로 만든다. 서버는 동시성마다 새로 띄운다.
- 내 로컬 개발 환경에서 코딩 에이전트·RAG 앱·테스트 스크립트가 같은 모델 서버를 동시에 부르는가? 그렇다면 단일 요청 벤치마크로 고른 엔진이 맞는가?
- `--gpu-memory-utilization`을 0.5·0.7로 바꿨을 때 KV 풀 크기와 대기 발생이 어떻게 달라지고, macOS·다른 앱과 메모리 경합은 없는가?

## 읽을 때 주의할 점
- vLLM 프로젝트가 자기 플러그인을 소개한 글이다. 비교 벤치마크는 공개돼 재현 가능하지만 설계와 실행은 발표 측이 했다.
- 그래프의 세부 수치(동시성별 TTFT 초 단위 값)는 그림으로만 제시된다. 본문 표로 확인되는 것은 패딩 비교와 MTP 비교다.
- 실제 사용자·기업의 운영 사례는 원문에 없음.
