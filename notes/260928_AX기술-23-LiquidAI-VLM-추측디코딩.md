# VLM 추측 디코딩은 디코드만 빨라진다 — LFM2.5-VL-DSpark

> 정리일: 2026-09-28
> 출처: [Hugging Face Blog (Liquid AI) — Accelerating vision-language models with LFM2.5-VL-DSpark](https://huggingface.co/blog/LiquidAI/lfm2-5-vl-dspark)
> 발행일: 2026-09-24
> 원문 언어: 영문

## 한 문장 인사이트
이 글은 비전-언어 모델(VLM)의 느린 생성 속도에 대해 **텍스트용 추측 디코딩 드래프터를 그대로 VLM에 붙이는 방법**을 제시한다. 근거는 6개 비전 과제에서 잰 디코드·전체 지연 개선이고, 한계는 **이미지 인코딩과 프리필은 빨라지지 않아 전체 개선이 디코드 개선보다 작다**는 점이며, 내 작업에서는 **요청 한 건의 시간을 이미지 인코딩·프리필·디코드로 나눠 재는 것**부터 확인해 보겠다.

## 원문 요약
- Liquid AI가 3B VLM **LFM2.5-VL-3B**용 실험적 드래프트 모델 **LFM2.5-VL-3B-DSpark**를 공개했다.
- 추측 디코딩(speculative decoding)은 작은 드래프터가 토큰 여러 개를 먼저 제안하고, 본 모델(target)이 한 번에 검증하는 방식이다. 본 모델이 모든 토큰을 검증하므로 **greedy 출력은 본 모델 단독과 같다**.
- 드래프터는 본 모델의 특정 층 hidden state를 받아 k개 후보 토큰 블록을 만든다. 이미지 패치와 텍스트 토큰이 그 층 전에 같은 차원으로 투영되므로 **텍스트 모델용 알고리즘을 바꾸지 않고** 쓴다.
- 드래프터는 4층 attention-only 구조, 약 **280M 파라미터로 본 모델 대비 8.9%** 늘어난다.
- llama.cpp, MLX-VLM, SGLang에서 첫날부터 지원한다(각각 별도 PR 빌드 필요). Safetensors와 GGUF로 배포한다.

> "Speculative decoding speeds up only decode, not vision encoding or prefill."
> (추측 디코딩은 디코드만 빠르게 하고, 비전 인코딩과 프리필은 빠르게 하지 않는다.)

## 핵심 주장과 근거
- **주장 1: 메모리를 조금 더 쓰고 출력 품질 변화 없이 디코드를 크게 빠르게 한다.**
  - 근거(자체 측정, 블록 크기 8, MMSpec 기반 6개 과제: 일반 VQA·텍스트 VQA·캡셔닝·차트 VQA·복합 추론·멀티턴 대화):
    - M5 Max + MLX: 디코드 **2.30~3.13배**, 전체 지연 **1.56~2.62배**
    - M3 Ultra + llama.cpp: 디코드 1.57~2.14배, 전체 1.30~1.77배
    - H100: 디코드 최대 **2.66배**, 전체 1.64~2.27배
- **주장 2: 드래프터 구성은 층 수·블록 크기 실험으로 정했다.**
  - 근거: 3·4·5층 비교 후 4층·블록 9로 학습. 비전-언어 SFT 데이터를 예상 서비스 과제에 가중해 10 epoch 학습했고, 수락률(acceptance)은 학습 토큰이 늘수록 오르다가 체감했다. 추론 시 하드웨어에 따라 블록 8 또는 9를 권한다.
  - 파라미터 구성: 디코더 4층 193.0M, hidden-state 투영 21.0M, Markov head 65.5M, 합계 279.5M.
- **한계·반론(원문이 직접 밝힘):**
  - VLM은 이미지가 먼저 비전 인코더를 거치고, 언어 모델이 수백 개의 시각 토큰과 텍스트를 프리필한다. 엣지 기기는 연산력이 작아 **프리필이 전체 지연에서 차지하는 몫이 크다**.
  - 추측 디코딩은 이 구간을 줄이지 못하므로 전체 개선은 가속되지 않는 부분에 막힌다(**암달의 법칙**). 그래서 디코드 3.13배가 전체로는 2.62배 이하가 된다.
  - 모델 스스로 "실험적(experimental)" 릴리스라고 부른다.

## 읽고 얻은 관점
- "몇 배 빨라졌다"는 숫자는 **어느 구간을 잰 것인지**부터 봐야 한다. 디코드 속도와 사용자가 체감하는 전체 지연(TTFT 포함)은 다른 지표다.
- 출력이 짧은 VLM 과제(캡션, 짧은 VQA)일수록 디코드 몫이 작아 추측 디코딩 효과가 줄어든다. 반대로 긴 답변·멀티턴에서 효과가 커질 것이다. 이는 원문 구조에서 끌어낸 해석이다.
- 추측 디코딩은 정확도를 건드리지 않는 "무손실" 가속이라 도입 판단이 비교적 단순하다. 비용은 메모리 8.9%와 서빙 스택 버전 의존성이다.
- 엣지 VLM의 다음 병목은 비전 인코더·프리필이다. 원문도 M5의 GPU 뉴럴 가속기가 이 격차를 줄인다고 언급한다.

## 적용 질문
- 작은 실험: Mac에서 `mlx_vlm.server`로 LFM2.5-VL-3B를 드래프터 유무 두 가지로 띄우고, 같은 이미지 20장에 "한 줄 캡션"과 "5문장 설명" 두 프롬프트를 보내 **TTFT·디코드 tok/s·전체 지연**을 따로 기록한다. 응답의 `draft_n / draft_n_accepted`로 수락률도 본다.
- 내 VLM 서비스 요청에서 이미지 인코딩·프리필·디코드가 각각 몇 %를 차지하는가? 디코드가 절반 미만이면 추측 디코딩보다 이미지 해상도·시각 토큰 수를 먼저 줄여야 하지 않는가?
- 드래프터를 붙였을 때 greedy가 아닌 샘플링 설정에서도 출력이 같은지, 서빙 프레임워크 버전 고정은 어떻게 관리할 것인가?

## 읽을 때 주의할 점
- 모델 개발사(Liquid AI)의 자체 벤치마크다. 경쟁 VLM·다른 드래프터와의 비교는 원문에 없음.
- H100 디코드 개선 범위의 하한은 원문에 "20.4x to 2.66x"로 표기돼 있어 하한 값이 불명확하다.
- 과제별 세부 수치와 TTFT 비중은 그림으로만 제시되고 본문 표로는 없다.
- 실제 서비스에 적용한 사례나 운영 지표는 원문에 없음.
