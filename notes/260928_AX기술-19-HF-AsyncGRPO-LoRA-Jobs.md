# LoRA 어댑터만 버킷으로 주고받아, NCCL 없이 여러 머신에서 비동기 GRPO를 돌렸다

> 정리일: 2026-09-28
> 출처: [Hugging Face Blog — Async GRPO with LoRA across HF Jobs: a bucket, a proxy, and no NCCL](https://huggingface.co/blog/asyncgrpo-lora-hfjobs)
> 발행일: 2026-09-10
> 원문 언어: 영문

---

## 한 문장 인사이트
이 글은 **학습기와 추론 서버가 같은 노드·네트워크를 공유하지 못할 때 강화학습 가중치를 어떻게 동기화하느냐**는 문제에 대해 **수 MB짜리 rank-1 LoRA 어댑터만 공유 스토리지 버킷으로 넘기고, 작은 프록시가 KV 캐시 기준으로 요청을 나누는 구성**을 제시한다. 근거는 **Qwen2.5-Math-1.5B 500스텝 실험 다섯 번과 대시보드 지표**이고, 한계는 **1.5B 소형 모델·단일 수학 데이터셋 규모의 검증**이다. 내 작업에서는 **학습 속도를 올리기 전에 병목이 학습 쪽인지 생성 쪽인지 지표로 먼저 가리는 방식**을 확인해 보겠다.

## 원문 요약
- Hugging Face TRL의 `AsyncGRPOTrainer`가 **TRL v1.14**부터 LoRA 어댑터를 학습하고, 전체 모델 대신 **어댑터만 vLLM에 동기화**할 수 있게 됐다(PR #7017).
- HF Jobs는 컨테이너 하나가 VM 하나에서 돌고 Job 사이에 네트워크 경로가 없다. 저자들은 **학습기 Job 1개 + vLLM Job 2~3개**를 따로 띄우고, 모든 Job에 같은 **Storage Bucket**을 같은 경로로 마운트해 공유 파일시스템으로 썼다.
- 학습기는 몇 스텝마다 어댑터를 버킷에 저장하고 경로를 vLLM의 `/v1/load_lora_adapter`로 보낸다. TRL과 vLLM 코드는 바꾸지 않았다.
- 학습기 Job 안의 **작은 프록시**가 인증 헤더를 붙이고, 같은 프롬프트의 롤아웃을 KV 프리픽스를 가진 복제본으로 보내며, 어댑터 로드를 모든 복제본에 방송한다.
- 같은 레시피로 다섯 번 실험해 500스텝 학습 시간을 **3시간 27분 → 53분**으로 줄였다. 세 Job 비용은 시간당 약 20달러다.

## 핵심 주장과 근거
- **주장 1: 강화학습에는 rank-1 LoRA로 충분하고, 그래서 동기화가 가벼워진다.**
  - 근거: Thinking Machines의 "LoRA Without Regret"을 인용해, 정책 경사 RL에서 에피소드당 정보량이 적어 rank-1로도 전체 미세조정과 맞먹는다고 설명한다. 1.5B 모델의 rank-1 어댑터는 수 MB, 전체 모델은 약 3GB다.
  - 실험: 500스텝 동안 보상 0.145 → 0.438, 학습기와 vLLM의 정책 일치 비율(`ratio`)이 **모든 스텝에서 1.000**, 126회 동기화 × 2복제본 = **252회 어댑터 로드 모두 성공**.
  - 동기화 1회: 30.8초 → 중앙값 8.5초.
- **주장 2: 프리픽스 기반 라우팅으로 중복 prefill을 줄인다.**
  - 방식: 16토큰 블록을 어댑터 이름으로 시작하는 연쇄 해시로 묶고, 모든 복제본이 본 블록(채팅 템플릿·시스템 프롬프트)은 "공통"으로 빼고 나머지로 복제본을 고른다. 한 복제본이 8건 넘게 앞서 있으면 캐시를 포기하고 여유 있는 쪽으로 보낸다.
  - 결과: 64,728회 롤아웃 중 **친화 적중 84.5%**, 새 프롬프트 14.2%(이론 최소 12.5%), 넘침 1.3%.
- **주장 3: 비동기 RL은 파이프라인이라, 한쪽만 빠르게 하면 소용없다.**
  - 근거: 롤아웃 대기 시간과 백프레셔 시간, 큐 크기를 함께 보고 병목 위치를 판정했다.
  - Run 1: 스텝의 96%가 forward+backward, MFU 3.9% → 학습기 병목.
  - Run 2: 시퀀스를 한 행에 채우는 토큰 예산 배칭(16,384) → 스텝 22.9초 → 5.9초. vLLM을 건드리지 않았는데 생성 속도가 4.6k → 25k tokens/s로 올랐다.
  - Run 3: 그래디언트 체크포인팅을 끄자 병목이 생성 쪽으로 넘어갔다.
  - Run 4: 복제본을 3개로 늘려도 효과가 없었다. 원인은 vLLM이 아니라 클라이언트의 동시 요청 상한 128이었다.
  - Run 5: 상한을 384로 올려 스텝 중앙값 4.8초, MFU 23.5%, 전체 3.9배 빠르고 31% 더 많은 샘플로 비슷한 보상 곡선.
- **한계·반론**
  - 1.5B 모델, 수학 데이터셋 1,460문항, rank 1 설정 하나에서의 결과다. 큰 모델·다른 과제에서의 동기화 시간과 품질은 원문에 없다.
  - 샘플이 오래 기다리며 평균 staleness가 1.5 → 2.0 버전으로 늘었다. 상한(4) 안이지만 속도와 정책 최신성 사이의 교환이다.
  - Python asyncio 프록시는 이 규모에서만 병목이 아니었다고 쓴다. 더 큰 트래픽은 더 빠른 언어가 필요할 것이라 본다.

## 읽고 얻은 관점
- 분산 학습의 통신 문제를 네트워크(NCCL) 대신 **"동기화할 대상을 작게 만든다"**로 풀었다. 어댑터가 작으니 파일 버킷이면 충분하다.
- 성능 개선의 대부분은 모델이 아니라 **샘플 패킹 방식·체크포인팅 기본값·클라이언트 상수** 같은 시스템 설정에서 나왔다. GPU를 더 붙이는 것(Run 4)은 효과가 없었다.
- 원칙이 명확하다. 서로 반대인 두 지표(학습기 대기 vs 생성 백프레셔)가 동시에 높으면 안 되고, 어느 쪽이 높은지가 병목 위치를 알려 준다.
- 어댑터 로드를 "전부 성공 아니면 롤백"으로 처리해, 같은 정책 이름이 복제본마다 다른 가중치를 가리키지 않게 한 점이 실무적이다.

## 적용 질문
- 내 학습·추론 파이프라인에서 **양쪽의 대기 시간을 각각 로깅**하고 있는가? 없다면 GPU를 늘리기 전에 그것부터 붙일 수 있는가?
- 기본값(그래디언트 체크포인팅, 배치 크기 1, 동시 요청 상한)이 내 모델 크기·GPU 메모리에 맞는지 확인해 본 적이 있는가?
- 여러 추론 서버에 같은 요청 접두어가 반복되는 서비스(에이전트의 긴 도구 설명 등)라면, 프리픽스 기준 라우팅으로 prefill을 얼마나 줄일 수 있는가?

## 읽을 때 주의할 점
- Hugging Face 엔지니어가 자사 서비스(HF Jobs·Storage Buckets)와 라이브러리(TRL)로 한 실험 글이다. 수치는 모두 저자들의 trackio 로그 기준 자체 측정이다.
- 5번의 실험 중 Run 2~4는 중간에 멈췄다. 전체 500스텝을 끝까지 비교한 것은 Run 1과 Run 5뿐이다.
- 시간당 약 20달러는 이 구성(학습기 h200×2, vLLM h200 각 1대)의 비용이다. 다른 규모의 비용은 원문에 없다.
