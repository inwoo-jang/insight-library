# Shopify, 운영 중 실패한 대화를 매일 모델 가중치로 되돌려 서빙 비용을 96% 줄였다

> 정리일: 2026-09-28
> 출처: [PyTorch Blog — How Shopify built a continual learning loop with PyTorch and vLLM](https://pytorch.org/blog/how-shopify-built-a-continual-learning-loop-with-pytorch-and-vllm/)
> 발행일: 2026-09-22
> 원문 언어: 영문

---

## 한 문장 인사이트
이 기업은 **판매자 질문에 답하는 GraphQL 에이전트가 프런티어 모델로는 느리고 비싸며 운영 실패에서 배우지 못하는** 병목을 해결하기 위해 AI를 **품질 정의→판정 모델 보정→실패 복구→SFT·GRPO 재학습의 지속학습 루프**에 적용했다. 성과는 **판정 점수와 서빙 비용·지연**으로 확인해야 하며, 확산의 관건은 **품질을 루브릭과 사람 합의로 먼저 정의하는 검증**이다. 우리 서비스에 적용한다면 **실패 대화 25건을 루브릭으로 두 사람이 따로 채점해 합의도를 재는 실험**부터 해보겠다.

## 원문 요약
- Shopify는 프런티어 모델로 AI 기능을 빠르게 출시한 뒤, 운영 트래픽에서 나온 실패를 매일 모델 가중치에 반영하는 **지속학습 루프(flywheel)**를 만들었다. Shopify Engineering 블로그 글을 PyTorch 블로그에 옮겨 실었다.
- 대표 사례는 판매자의 질문을 Admin GraphQL API 쿼리로 바꿔 실행하고 답하는 **GraphQL 에이전트**로, 운영에서 **분당 최대 2,000건**을 처리한다.
- 루프는 ① 품질 루브릭 정의 ② LLM 판정 모델(judge) 보정 ③ 가중치를 건드리지 않는 하네스 개선(autoresearch) ④ 실패 대화 복구 후 SFT·GRPO 재학습 ⑤ 시스템 프롬프트 압축(gisting) 순서로 돈다.
- 복구 파이프라인은 매일 돌고, 누적 데이터로 전체 파라미터 미세조정과 GRPO를 같은 주기로 반복한다. 서빙은 vLLM으로 한다.
- Shopify는 이 루프로 프런티어 모델보다 높은 품질, 낮은 지연, **서빙 비용 96% 절감**을 얻었다고 쓴다.

> "When you get the evals or specs wrong, everything downstream optimizes the wrong behavior."
> (평가나 명세를 잘못 잡으면, 그 뒤의 모든 단계가 잘못된 행동을 최적화한다.)

## 적용 구조와 성과
- **대상 업무와 병목:** 판매자 질문(예: 재고가 거의 떨어진 상품은?)에 맞는 GraphQL 쿼리를 짜서 실행하고 답하는 업무. 프런티어 모델은 규모가 커지면 느리고 비싸며, 운영에서 나온 실패가 가중치에 반영되지 않고 프롬프트·라우팅 규칙·하네스 코드에만 쌓였다.
- **적용 단계와 방식:**
  - **품질 정의:** 완전성·실행·응답 품질·안전성 네 기준의 루브릭을 만든다. 무작위 표본 25건을 최고 전문가 두 명이 따로 채점해 **Cohen's kappa**로 합의도를 재고, 0.2 수준이면 루브릭을 고친다. 사람 간 합의도가 판정 모델의 상한이다.
  - **판정 모델 보정:** DSPy와 GEPA·ACE 최적화기로 판정 프롬프트를 보정한다. 과거 A/B 테스트 결과의 방향을 맞히는지 백테스트하고, 특정 행동을 일부러 나쁘게 만들어 해당 기준 점수만 떨어지는지 확인한다.
  - **하네스 개선:** 에이전트가 프롬프트·도구 정의·하네스 코드를 바꿔 보고 판정 점수가 오르면 남기는 autoresearch 루프를 마크다운 설정 파일 하나로 돌린다.
  - **실패 복구와 재학습:** 판정 점수가 낮은 운영 대화를 프런티어 추론 모델 패널이 비평하고, 중재자가 수정 지시를 만들어 사용자 턴 앞에 넣은 뒤 재생한다. 통과하면 학습 궤적이 되고, 실패하면 Toloka 전문가가 같은 루브릭으로 수정한다. 이 궤적으로 작은 모델에 SFT(추론 포함)를 하고, 판정 점수를 보상으로 **GRPO**를 한다.
  - **프롬프트 압축:** 모델 가중치는 고정한 채 학습된 gist 토큰으로 긴 시스템 프롬프트를 대체한다.
- **성과(모두 Shopify 자체 측정·추정):**
  - 서빙 비용: 프런티어 모델 기준 **연 약 2,700만 달러 추정 → 약 100만 달러 수준**, 96% 절감. 원문은 "could"로 쓴 추정이다.
  - 품질: 특화 모델이 프런티어 모델 성능을 넘었다고 쓴다. 구체적 점수는 원문에 없다.
  - 프롬프트: 약 6,000토큰 → 약 1,500 gist 토큰. 판정 기준 품질 손실은 측정되지 않았다고 쓴다.
  - 부하 시험(분당 350건): 첫 토큰 지연 약 19%, 전체 지연 약 38% 감소. 초당 요청 약 16%, 초당 출력 토큰 약 12% 증가, 같은 트래픽에 GPU 약 14% 절감.

## 읽고 얻은 관점
- 루프의 출발점은 모델이 아니라 **"좋은 답이 무엇인가"를 사람끼리 합의하는 일**이다. 루브릭이 곧 판정 모델의 첫 프롬프트이고, 판정 점수가 곧 강화학습의 보상이 된다.
- 판정 모델을 믿기 전에 **과거 A/B 결과 백테스트와 일부러 망가뜨리는 시험**으로 검증한다. 오프라인 지표를 온라인 지표에 묶는 구체적인 방법이다.
- 순서가 분명하다. 프런티어 모델로 출시 → 가중치를 건드리지 않는 하네스 개선이 정체되면 → 그때 파라미터 학습으로 넘어간다.
- 실패 대화가 버그 리포트·슬랙 스레드로 흩어지지 않고 자동으로 학습 데이터가 되는 구조가 "운영 경험의 축적"을 실제 자산으로 만든다.

## 적용 질문
- 내 서비스의 "좋은 응답"을 3~4개 기준과 점수별 예시로 쓸 수 있는가? 두 사람이 따로 채점했을 때 kappa는 얼마나 나오는가?
- 운영 로그에서 **판정 점수가 낮은 대화를 자동으로 모으는 경로**가 있는가, 아니면 실패가 여전히 이슈 트래커에 흩어지는가?
- 프런티어 모델 API 비용이 커지는 기능 중, 반복적이고 도메인이 좁아 작은 특화 모델로 옮길 만한 것은 무엇인가?

## 읽을 때 주의할 점
- Shopify가 직접 쓴 글을 PyTorch 커뮤니티용으로 옮긴 것이다. 모든 수치는 자체 측정이며, 96% 비용 절감은 평균 토큰 단가로 계산한 추정이다.
- "프런티어 모델보다 높은 품질"의 비교 점수, 사용한 모델 크기, 학습 주기별 품질 변화는 원문에 없다.
- 루프 전체가 가능한 전제는 분당 수천 건의 트래픽, GPU 학습 인프라, 외부 전문 주석사(Toloka)다. 작은 서비스에 그대로 옮길 수 있는 규모가 아니다.
